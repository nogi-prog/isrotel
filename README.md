# מערכת ניהול גלישות

מערכת לניהול גלישה חטיבתית: מי יוצא, באיזו פעימה, באיזה אוטובוס, עם מי בחדר, וכמה מנות להזמין.
כל הממשק בעברית ובכיווניות RTL.

התכנון המלא נמצא ב־[ARCHITECTURE.md](./ARCHITECTURE.md).

## הרצה

```bash
npm install
npm run seed     # נתוני דמו: מבנה ארגוני מלא (מפמ״ר ומטה), גלישה, 2 פעימות ו-4 מבני לינה
npm run dev      # שרת על 4000, לקוח על 5273
```

פתיחה בדפדפן: <http://localhost:5273>

`npm run dev` מריץ את השרת ואת הלקוח יחד — זה מה שצריך ברוב המקרים. אם מריצים רק את הלקוח
(`npm run dev:web`) בלי השרת, הלקוח יציג "השרת אינו זמין" והטרמינל יסביר מה להריץ.

| --- | --- | --- |

| `4000001` | שירה אופיר, אופרטיבי | ניהול גלישות, שיבוצים, הזמנת מזון - **וגם** שיבוץ מדור אופרטיבי שלה |
| `4000002` | אבי שגב, רת״ח | אישורים וכל האנשים בתחום |
| `4100001` | רמ״ד מדור תוכנה | שיבוץ האנשים שלו לגלישה, האצלה לר״צים, אישורים |
| `4100002` | ר״צ צוות אלון | שיבוץ הצוות שלו (רק אם הרמ״ד האציל לו) |

מספר אישי שאינו במסד יפתח את מסך ההרשמה הראשונית — כך בודקים את זרימת "כניסה ראשונה + אישור מפקד".

### פקודות נוספות

```bash
npm test         # 113 טסטים: מנועי השיבוץ, מיגרציות, ואינטגרציה מלאה על ה-API
```

## מבנה

```

  db/           סכמה (schema.sql), פתיחת מסד, זריעת דמו
  lib/          auth, סיסמאות, שגיאות, היררכיה ארגונית, עזרי גלישות, התראות
  services/     busAllocation.ts, dormAllocation.ts  ← מנועי השיבוץ (פונקציות טהורות)
  routes/       auth, users, trips, signups, buses, dorms, reports, notifications
  api.test.ts   טסט אינטגרציה מקצה לקצה
web/src
  pages/        מסכי חייל, מפקד ואופרטיבי
  components/   שלד העמוד ורכיבי UI
  lib/          api client, auth context, מילון המונחים בעברית
```

## זרימת העבודה במערכת

1. **כניסה ראשונה** — המשתמש ממלא שם, מין, מספר אישי, סיסמה, מפקד והעדפת תזונה. בחירת המפקד היא מהדרג
   שמעליו בלבד: חייל → ר״צ, ר״צ → **רמ״ד או אופרטיבי**, רמ״ד → רת״ח, רת״ח → **מפמ״ר** — עם חיפוש
   חופשי לפי שם או שם יחידה. המפמ״ר הוא ראש השרשרת ונרשם בלי מפקד; רישום כזה (וגם רישום שאין מעליו
   מפקד מאושר במערכת) מאושר על ידי האופרטיבי. הרישום ממתין לאישור, ועד אז אין גישה לשאר המערכת.
2. **האופרטיבי מפרסם גלישה** — הגלישה נכנסת למצב `LAUNCHED`. מסך היצירה (`/manage/new`) עומד בנפרד
   מרשימת הגלישות ובו שלושה קלטים: תאריך הפרסום, המפקדים (רמ״ד/רת״ח) שקיבלו את משימת שיבוץ האנשים,
   ופעימות היציאה. לפעימה יש תאריך יציאה בלבד - היא גל של יום אחד. שם הגלישה נוצר אוטומטית
   ("גלישה #1"), ושמות הפעימות נגזרים מסדר היציאה: הראשונה היא **חלוץ**, ואחריה **פעימה 1**,
   **פעימה 2** וכן הלאה. אחר כך האופרטיבי מגדיר מבני לינה ושולח למפקדים הודעה שעליהם לשבץ.
   **הוא אינו משבץ אנשים בעצמו.**
3. **המפקדים משבצים את האנשים שלהם ומגישים את הרשימה** — רמ״ד/רת״ח שקיבל את המשימה בוחר את
   האנשים בעצמו, או מאציל את השיבוץ לר״צים שתחתיו. שיבוץ של מי שקיבל את המשימה נכנס מיד; שיבוץ של
   ר״צ באצילה ממתין לאישור המאציל. **חייל אינו משבץ את עצמו.** בסיום הוא **מגיש את הרשימה**,
   והאופרטיבי רואה מי הגיש ומי לא.
4. **המשובץ משלים את הפרטים שלו** — בחירת עד 3 שותפים לחדר ואישור העדפת התזונה. המערכת חוסמת בחירה
   שאינה חוקית: בנים עם בנים, חיילים עם חיילים, וחייל רק מתוך המדור שלו. אין לו אפשרות להסיר את
   עצמו מהגלישה - זו פעולה של המפקד.
5. **מי שנוסף ליחידה אחרי ההגשה** — אם אושר רישום של אדם חדש תחת מפקד שכבר הגיש, המפקד מקבל התראה,
   והאדם מסומן במסך השיבוץ שלו בכרטיס נפרד ("נוספו ליחידה שלך אחרי ההגשה") עם כפתור הוספה לגלישה.
   זה אפשרי **כל עוד האופרטיבי לא הגיש את הגלישה**.
6. **האופרטיבי מגיש את הגלישה** — מכאן רשימת המשתתפים קפואה: אף אחד אינו מוסיף או מסיר אנשים, ואי
   אפשר לאשר בקשות ממתינות. לפני ההגשה הוא רואה אילו מפקדים טרם הגישו וכמה בקשות ממתינות. מי שכבר
   שובץ **כן** ממשיך להשלים שותפים ותזונה, כי שיבוץ הלינה מתבסס על זה. ההגשה הפיכה
   ("פתיחת השיבוץ מחדש").
7. **האופרטיבי נועל שיבוץ אוטובוסים** — המערכת מחלקת לאוטובוסים בקיבולת 50 תוך שמירה על יחידות שלמות.
   כל אחד רואה את מספר האוטובוס שלו, המפקדים רואים את האנשים שלהם, האופרטיבי את הרשימה המלאה.
8. **האופרטיבי נועל שיבוץ לינה** — המערכת משבצת לפי העדפות. מי שלא קיבל אף העדפה, או שלא נמצאה עבורו
   מיטה, נפתח כבעיה אצל המפקד שלו יחד עם הצעות חלופיות מאותו מדור.
9. **הזמנת מזון** — האופרטיבי מקבל את מספר המנות מכל סוג תזונה, לפי פעימה ובסך הכל. פעימה היא
   יציאה של יום אחד, ולכן מספר המנות הוא מספר המשתתפים כפול 3 ארוחות.

## הערות תפעול

- `npm audit` מדווח על שתי התראות ב־`react-router` בדרגה high. שתיהן נוגעות למצב RSC של הספרייה,
  שאינו בשימוש כאן (האפליקציה היא SPA צד-לקוח בלבד), ואין כרגע גרסה מתוקנת בענף 7.x — גרסאות
  מוקדמות יותר סובלות מיותר בעיות.
- `SESSION_SECRET` מוגדר לסוד פיתוח כברירת מחדל. בייצור חובה להגדיר אותו כמשתנה סביבה.
- מסד הנתונים נמצא ב־`server/data/trip-organize.db`. אפשר לשנות בעזרת `DB_FILE`.
- ההתחברות היא במספר אישי וסיסמה (מגובבת עם scrypt), בלי ספק זהויות חיצוני. אין איפוס סיסמה
  עצמאי — "שכחתי סיסמה" פותח בקשה שרק האופרטיבי יכול לטפל בה, ומקבל סיסמה זמנית להעביר למשתמש
  מחוץ למערכת.
